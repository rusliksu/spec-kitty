# Приёмка миссии в объявленном checkout

Дата: 2026-09-12. Продолжение D-18; объём одобрен пользователем отдельным сообщением.

## Согласованный результат

`accept --owned-checkout <path>` читает миссию и сохраняет результат приёмки в
объявленной рабочей копии. Незавершённая миссия остаётся неготовой. Основной
checkout и одноимённая миссия в нём не меняются. Без флага сохраняются прежние
результаты и форма вызовов. Чужое объявление отклоняется до первой записи.

## План исправления

1. Проверять объявление через существующий `checkout_ownership`, затем сохранять
   явный корень в данных приёмки. Не использовать глобальную настройку корня.
2. Передавать этот корень в существующие kind-aware resolver для metadata,
   planning, tasks, status и acceptance matrix; сохранить проверку topology и ref.
3. Довести явный корень через сохранение метаданных, cutover и остаточные commit.
   Старую канонизацию пути не применять к явно объявленной рабочей копии.
4. Проверить реальные linked worktree: готовая и незавершённая миссии,
   одноимённая миссия в основном checkout, чужой checkout, вызов без флага,
   неизменность основного HEAD и файлов, чистое сохранение результата.
5. Выполнить независимое ревью и релевантные тесты/CI. Merge, release и ручное
   закрытие старых WP в этот пакет не входят.

## Исходные доказательства

Исходная команда `accept --diagnose` возвращает `mission_not_found` (D-18/EV-025).
В `collect_feature_summary` и post-accept helpers отсутствует передача явного
корня. Проверка пути записи выявила дополнительное условие: `canonicalize_feature_dir`
перенаправляет linked mission в основной checkout при наличии одноимённой миссии.
Проверка только отсутствующей в основном checkout миссии недостаточна.

Рабочая ветка: `codex/accept-owned-checkout`, база `b0f58f49b` из PR #27.
Оригинальный PR и lifecycle старой миссии не изменяются этой рабочей копией.

Проверены реальные worktree, включая одноимённую миссию в основном checkout.
