# Приёмка миссии в объявленном checkout

Дата: 2026-09-12. Продолжение D-18; объём одобрен пользователем отдельным сообщением.

## Согласованный результат

`accept --owned-checkout <path>` читает миссию и сохраняет результат приёмки в
объявленной рабочей копии. Незавершённая миссия остаётся неготовой. Основной
checkout и одноимённая миссия в нём не меняются. Без флага сохраняются прежние
результаты и форма вызовов. Чужое объявление отклоняется до первой записи.

## План исправления

1. Проверять объявление через существующий `checkout_ownership`, затем сохранять
   явный корень в данных приёмки. Не использовать глобальную настройку корня.
2. Передавать этот корень в существующие kind-aware resolver для metadata,
   planning, tasks, status и acceptance matrix; сохранить проверку topology и ref.
3. Довести явный корень через сохранение метаданных, cutover и остаточные commit.
   Старую канонизацию пути не применять к явно объявленной рабочей копии.
4. Проверить реальные linked worktree: готовая и незавершённая миссии,
   одноимённая миссия в основном checkout, чужой checkout, вызов без флага,
   неизменность основного HEAD и файлов, чистое сохранение результата.
5. Выполнить независимое ревью и релевантные тесты/CI. Merge, release и ручное
   закрытие старых WP в этот пакет не входят.

## Исходные доказательства

Исходная команда `accept --diagnose` возвращает `mission_not_found` (D-18/EV-025).
В `collect_feature_summary` и post-accept helpers отсутствует передача явного
корня. Проверка пути записи выявила дополнительное условие: `canonicalize_feature_dir`
перенаправляет linked mission в основной checkout при наличии одноимённой миссии.
Проверка только отсутствующей в основном checkout миссии недостаточна.

Рабочая ветка: `codex/accept-owned-checkout`, база `b0f58f49b` из PR #27.
Оригинальный PR и lifecycle старой миссии не изменяются этой рабочей копией.

## Красное воспроизведение

Новые сценарии: 6 failed, 1 passed; все шесть отказов вызваны отсутствием опции --owned-checkout. Контроль без объявления сохраняет mission_not_found. Проверены реальные worktree, включая одноимённую миссию в основном checkout. Команда: pytest tests/specify_cli/cli/commands/test_accept_owned_checkout.py -q --tb=line --show-capture=no -p no:cacheprovider.

## Уточнения по результатам реализации и ревью

Объявление одной рабочей копии не расширяется на второй coordination checkout.
Перед изменениями проверяются действительные поверхности metadata, status и
acceptance matrix; перед commit — совпадение текущей и целевой незащищённой ветки.
Общие критерии приёмки сохраняются.

Передача корня потребовалась также в dirty-фильтре, чтении topology и определении
lifecycle: одноимённая миссия в основном checkout иначе скрывала изменённый
issue-matrix либо подменяла целевую ветку на main. Оба контрпримера воспроизведены
красными тестами до исправления.

В режиме с объявлением cutover выполняется до записи приёмки. Проверяется полный
результат: error, flipped и verify.ok. Для трёх отказов (error, отрицательная
верификация без error, исключение) красные тесты подтвердили прежний ложный успех
или уже записанную приёмку. Исправленный путь не создаёт acceptance/residual commit
при отказе; диагностическая матрица или seed-артефакты могут остаться локально.
Поведение и порядок вызовов без флага сохранены.

Независимое повторное ревью: APPROVE, блокирующих замечаний нет. Старый fallback
для синтезированного составного handle в общем resolver не менялся: CLI приёмки
передаёт существующее имя каталога, и эта ветвь здесь недостижима.

Мутационная проверка: временная подмена в памяти удаляла effective_root из dirty
gate. Сценарий с issue-matrix стал красным (команда ложно приняла миссию), контроль
со spec.md остался зелёным. Исходники при мутации не менялись.

Настоящая диагностика D-18 теперь находит миссию в объявленной рабочей копии и
возвращает ok=false: WP01 in_progress, WP02 planned, approved/done отсутствуют;
есть прежние metadata/path blockers. Статусы не исправлялись вручную, lenient
не применялся. Основной checkout чист, HEAD 78c1e9ab1; frozen lifecycle.jsonl
сохранил blob b0c8620e5b611c7ff53f6014a31a27328d7c7509.
