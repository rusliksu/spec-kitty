# Контракт выбранной рабочей копии

## Вход и выбор источника

Опция `--owned-checkout PATH` явно задаёт корень, в котором команда ищет миссию.
До чтения состояния и любой записи путь проверяется существующим
`resolve_ownership_claim` относительно репозитория вызова. Каталог другого
репозитория, вложенный каталог и повреждённый указатель Git не становятся целями записи.
Без опции сохраняются прежние источники, проверки и форма вызовов зависимостей.

Если обе копии содержат миссию с разными файлами, выбранная копия остаётся источником
данных. Диагностика `owned_mission_divergence` выводится в stderr; stdout с JSON
остаётся пригодным для машинного чтения. Данные между копиями не объединяются.

## Переход и результат ревью

`agent tasks move-task` и `agent status emit` читают состояние и записывают события
в одну и ту же выбранную миссию. Журнал остаётся единственным источником состояния;
снимок и отметки подзадач выводятся из него. Обычные ограничения переходов сохраняются:
незавершённые подзадачи блокируют ревью, а некорректный структурированный результат
не создаёт событие одобрения.

При одобрении через `move-task` существующий механизм сохраняет документ ревью,
коммитит его в разрешённую ветку и проверяет сохранённые в Git байты. Выбор корня
сохраняется также при чтении предыдущего результата и компенсирующем откате.
Новый журнал или второй механизм записи не создаётся.

## Проверка изменений в одной ветке

Для явно выбранного связанного checkout миссии `single_branch` с реальными изменениями
кода проверка не требует выдуманного отдельного каталога реализации.
Используется существующий интерфейс разрешения workspace, который возвращает
реальный checkout и доказанный диапазон изменений:

- основа U — коммит настроенного upstream основной ветки репозитория;
- результат H — коммит HEAD выбранной ветки, совпадающей с целевой веткой миссии;
- U должен быть единственным общим предком из `git merge-base --all H U`;
- в диапазоне U..H должны быть изменения в `owned_files` проверяемой задачи,
  за исключением служебных каталогов планирования и состояния;
- тот же U используется для определения изменённых файлов при выборе тестов;
- результаты исходного прогона тестов читаются из выбранной копии;
- перед сохранением результата повторно проверяются ветка и HEAD.

Отсутствующая основа, detached HEAD, другая ветка, отставание от upstream,
неразрешимая задача и отсутствие реальной реализации дают отказ. Локальная устаревшая
основная ветка, `HEAD~1` и имя текущей ветки не подставляются вместо доказанной основы.
История Git и состояние задачи не дописываются для обхода этих проверок.

## Планирование и чтение

`list-tasks`, `status validate` и `status lifecycle` читают выбранное состояние.
`finalize-tasks` проверяет состав задач и создаёт только отсутствующие начальные события
в выбранной копии; `--validate-only` не меняет её файлы. Поддержка
`map-requirements`, `migrate backfill-runtime-state` и `research` сохраняет
тот же явный выбор. Неподдерживаемый запуск из связанного checkout отказывает до записи.

## Проверяемые последствия

Исполняемые сценарии находятся в `tests/status/test_status_owned_checkout_seam.py`,
`tests/tasks/test_move_task_owned_checkout_seam.py`,
`tests/tasks/test_finalize_owned_checkout_seam.py` и
`tests/tasks/test_single_branch_owned_review.py`.
Они используют зарегистрированные Git worktree и проверяют фактические события,
содержимое документа ревью в Git, HEAD, индекс и файлы основной копии.
Проверка существующих маршрутов выполняется также прежними тестами и архитектурными
проверками без новых исключений, пропусков или ослабления порогов.
